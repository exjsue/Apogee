# Decisions

| Date | Decision | Reason |
|------|----------|--------|
| 2026-10-22 | Web app only for now, plain HTML/CSS/JavaScript, no frameworks. | Owner is a beginner and wants the simplest path to a working app; iOS native deferred. |
| 2026-10-22 | All data stored on-device in IndexedDB. No server, no accounts, no analytics. | Privacy-first product goal. |
| 2026-10-22 | Browser storage is not the sole copy of user data; export/import is required in v1. | persist() returned false in iPhone Safari and Firefox Focus during a one-off test, so data can be evicted. |
| 2026-10-22 | Primary test browsers: iPhone Safari and Firefox Focus. | Owner uses Firefox Focus daily; Safari is the iPhone default and uses the same WebKit engine as every iOS browser, so it is the baseline. |
| 2026-10-22 | Weights stored as entered (value plus unit), converted only for display and calculation. | Converting kg to lb and back with floating-point math drifts, and rounding on save would permanently change what the user typed. |
| 2026-10-22 | ES modules need HTTP(S) serving, not file://. | Browsers block module loading from local files. |
| 2026-10-22 | crypto.randomUUID() needs a secure context and must be verified on iPhone Safari and Firefox Focus. | It is unavailable on plain HTTP pages. |
| 2026-10-22 | Storage is split into rules (src/storage/store.js) and adapters (memory, IndexedDB) behind a small interface. | The rules can be tested in Node with no dependencies; only the thin IndexedDB adapter needs a browser to test. |
| 2026-10-22 | Saving a workout with its entries and sets, and deleting a workout, are each a single transaction. | All of it saves or none of it does, so a crash or error cannot leave orphaned entries or sets. |
| 2026-10-22 | No fake-IndexedDB library; the IndexedDB adapter is tested in a real browser page (tests/browser/index.html). | Keeps the dependency list empty, and a fake would not prove the real browsers behave. |
| 2026-10-22 | Saves check that referenced records exist (entry needs workout and exercise, set needs entry), inside the same transaction as the write. | Prevents dangling references; checking and writing in one transaction avoids a race between them. |
| 2026-10-22 | saveWorkoutWithDetails treats the lists as the workout's complete contents and deletes its stored entries and sets that are not in them. | Otherwise editing a workout and removing an exercise would leave the removed entry behind. |
| 2026-10-22 | Import is replace-everything and needs explicit confirmation (confirmReplace: true). No merge. | Merge semantics (duplicates, conflicts, deletions) are harder to reason about, and restoring a backup should be predictable. |
| 2026-10-22 | Import validates the whole file before any write, then applies it in one transaction. | A bad or damaged file cannot corrupt or half-replace existing data. |
| 2026-10-22 | Export has a plain-text form (exportToText) as a fallback for iOS download problems. Unverified on WebKit. | File downloads can misbehave on iOS; the text can be copied and saved by hand. Download and file picker still need testing on iPhone Safari and Firefox Focus. |
| 2026-10-22 | Import is strict: every field must be present, unknown fields are rejected, and each stored record must equal its file record exactly (non-canonical timestamps are rejected, nothing is defaulted). | An import must never invent or silently change values; a hand-edited or foreign file fails loudly instead. |
| 2026-10-22 | Import size limit is 50 MiB, counted in UTF-8 bytes, and is a parameter. | A 20-year heavy history is about 35-40 MB; the limit stops a wrong huge file from freezing the tab. Memory use on iPhone is unmeasured. |
| 2026-10-22 | Muscles are a fixed vocabulary of 18 ids (chest, front_delts, side_delts, rear_delts, biceps, triceps, forearms, traps, lats, upper_back, lower_back, abs, obliques, glutes, quads, hamstrings, calves, adductors). An exercise needs at least one primary muscle; unknown, duplicate and primary/secondary-overlapping muscles are rejected. | Free text would give "chest", "Chest" and "pecs" as three muscles, which breaks search, the later muscle diagram and importers. A fixed list is one mapping target. Adding an id later is safe; removing or renaming one needs a data migration. |
| 2026-10-22 | Equipment tags are a fixed vocabulary of 11 (barbell, dumbbell, kettlebell, ez_bar, machine, smith_machine, cable, resistance_band, bodyweight, bench, pull_up_bar). | Same reason as muscles: searchable, and a single target for importers. |
| 2026-10-22 | Exercise names and all notes are trimmed with whitespace runs collapsed to one space (so they are single-line). Names are limited to 80 characters, notes to 500, counted in characters. | Keeps stored text canonical and bounded; prevents "Squat" and " Squat " being different exercises. Multi-line notes would need a different rule. |
| 2026-10-22 | The page's Content-Security-Policy blocks all network access: default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'none'; img-src 'self' data:; base-uri 'none'; form-action 'none'. The dev server sends the same policy, and a test checks that they match. | Privacy-first: even a bug or a bad dependency cannot send data anywhere. A test also scans index.html and src/ for network APIs, markup injection, eval and off-origin links, with an empty allowlist. |
| 2026-10-22 | The built-in exercises (16 lifts, ids starting seed-) are stored in IndexedDB as ordinary records, and seeding is tracked by a seedVersion in meta: it runs only when the stored version is lower than the code's, adds missing ids only, and never overwrites. | Stored records are included in exports and imports, so a backup is complete. The version lets later releases add exercises without touching a user's edits. |
| 2026-10-22 | Blank or whitespace reps and weight are errors and never become 0; bodyweight is an explicit 0. Decimals accept "62.5" and "62,5" (a comma only with 1-2 digits after it); "1,500", "1.500,5", exponents, hex, Infinity and NaN are rejected. | JavaScript's Number("") is 0, which would silently log a bodyweight set. Ambiguous separators are rejected rather than guessed. |
| 2026-10-22 | An unfinished workout that started more than 12 hours ago (a parameter) is never continued silently: the Log tab offers Continue, Finish or Discard. Finish ends it at its last set, not at "now". Logging is blocked until it is resolved. | A forgotten workout from yesterday must not swallow today's sets or show a 20-hour duration. |
| 2026-10-22 | deleteSet removes an entry when its last set goes; discardWorkout refuses a finished workout; finishing a workout with no sets is refused. Each is one transaction. | No empty entries or orphans, and the discard path cannot erase history by accident. |
| 2026-10-22 | Weights are shown in the preferred unit (default lb, stored in meta); a set entered in the other unit shows the converted value with "entered X" beside it. Stored values never change. | Reinforces "stored exactly as entered"; the toggle is display only. The preference is not exported. |
| 2026-10-22 | The dev server uses a fixed port (8080) and refuses to start if it is taken, instead of choosing another. | IndexedDB is per origin, and an origin includes the port: another port would open an empty database and look like data loss. |
| 2026-10-22 | A set has 1 to MAX_REPS = 1000 reps, and a weight from 0 to MAX_WEIGHT_KG = 2500 once converted to kg (about 5511.55 lb). Both are named constants in model.js and are only checked, never stored, so no schema change. Messages say which rule broke: "weight can't be negative", "weight is above the maximum of 2500 kg", "reps is above the maximum of 1000". The check allows 1e-9 kg of float noise so a weight typed exactly on the limit in lb is accepted. | Without limits a typo such as 920319039 reps would be stored and break displays and any later statistics. The numbers are generous (the heaviest lifts ever recorded are well under 2500 kg) and easy to change. The limits apply to imports too, so a bad file is refused. |
| 2026-10-22 | Renamed log-view.js to workout-view.js because uBlock Origin blocked it, and Firefox Focus blocks trackers too. File names that match common blocker patterns break the app for users with blockers; avoid names like log, track, stat, ad. | Blockers match file names, so a module called log-view.js can fail to load. The rename keeps the module working under such blockers. |
| 2026-10-22 | A finished workout can be deleted from its History detail: Delete workout asks first, says it removes the workout and its N sets, cannot be undone, and suggests exporting; Cancel changes nothing. The rule lives in logger.deleteFinishedWorkout, which refuses an unfinished workout (that is what Discard is for) and an unknown id, then calls store.deleteWorkout (one transaction, so no orphans). Exercises are never deleted. | Deleting history is irreversible and there is no undo or trash, so the safeguards are the confirmation, the export suggestion and the single transaction. Keeping Delete and Discard as separate paths means one cannot remove the other kind of workout by accident. |
| 2026-10-22 | The app is hosted on GitHub Pages from a public repo (https://exjsue.github.io/Apogee/), because the source contains no user data. A read-only audit of all 15 commits found no secrets, personal data, local paths or email addresses other than noreply ones. This reverses the earlier TODO to make the repo private again. | The app needs no server and keeps all data on the device, so there is nothing private in the code to protect. Pages is free HTTPS hosting, which also gives iPhone testing the secure context that crypto.randomUUID() needs. |
| 2026-10-22 | The app's origin is exjsue.github.io, shared by every other Pages site under the account. IndexedDB is per origin, so any such site could read or delete the app's data (the database named in storage/schema.js). Do not host other sites on this account until the app has a custom domain. | Browser storage is isolated by origin, not by URL path, and a project site lives under the account's origin. The page's own CSP cannot prevent a sibling site from opening the same database. |
| 2026-10-22 | On Pages only the CSP meta tag applies. frame-ancestors, report-uri and sandbox cannot be set in a meta tag, and Pages does not let us send headers such as X-Content-Type-Options: nosniff or Cache-Control: no-store, so the page can be shown inside someone else's frame. | tools/serve.js sends the same policy plus nosniff and no-store locally, but a static host controls its own headers. Accepted for now: the app has no accounts, and the destructive actions (Delete workout, Replace everything) need a second confirming step, which limits but does not remove the risk of a framing page tricking someone into taps. A custom domain behind a host that allows headers would fix it. |
| 2026-10-22 | Pages publishes the whole repo root, including tests/, tools/, the docs and package.json. Accepted because the repo is public. A .nojekyll file makes Pages serve files as they are. | Everything in the repo is already public. The test page runs against its own throwaway database, never the app's. |
| 2026-10-22 | The app's real database name is defined once (APP_DB_NAME in src/storage/schema.js) and only src/ui/main.js uses it. createIdbAdapter has no default name and throws without one. tests/guard.test.js fails if anything under tests/ uses the constant or the exact name, or if the name is defined anywhere else. | The test page and the app share an origin, so a test that opened or deleted the app's database by mistake would destroy real data. A default name made that one forgotten argument away; a test now enforces the rule instead of relying on care. |
| 2026-10-22 | The rule "no network calls at runtime" is amended to: "No network calls at runtime except same-origin requests by the service worker, to cache the app's own files and check for updates. No third-party hosts, ever." (CLAUDE.md, Technical direction.) | Working offline needs the service worker to fetch the app's own files once and to look for new versions. That is the only network traffic the app ever makes, and it stays on the origin the app came from. tests/guard.test.js enforces it on sw.js: no URL of any kind, fetch only inside the fetch handler on the incoming request, a same-origin and GET-only check first, only the generated file list cached, no IndexedDB, no push or sync. The page itself still makes no requests (its policy keeps connect-src 'none'). |
| 2026-10-22 | Updates are user-controlled and never silent: a new service worker installs, then waits; the page shows "Update available" with a Reload button; only that click tells the worker to activate (the one skipWaiting, in the message handler), and the page reloads only after the switch. Another open tab is told to reload, and never reloads by itself. | A silently swapped worker can serve old code against newer data: a page running version N would suddenly get version N+1's files while the database may already have been changed by N+1. Making the switch an explicit click, followed by a reload, keeps code and data in step. A waiting worker still activates by the browser's own rules when every window of the app is closed; nothing old is running then, so that is safe, and it is documented in OFFLINE.md. |
| 2026-10-22 | The service worker's file list and cache version are generated, not typed: tools/build-sw-manifest.js follows index.html, the scripts' import graph and the manifest's icons and writes sw-manifest.js; the version is a SHA-256 over every listed file and sw.js, with line endings normalized. node --test fails if sw-manifest.js is stale or if the list differs from an independent crawl of what the app loads. The install is all or nothing (one failed file fails the whole install and leaves the old worker and cache as they were). | A hand-kept list would eventually miss a file and break offline use quietly, or serve a mix of old and new files. A hash of the contents makes every change a new cache, and refusing a partial install means an offline copy is never half old and half new. The generator is a small script that writes one committed file; it does not bundle or transform the app, so the files served are the source files (an exception to "no build tools yet" the owner approved with this task). |
| 2026-10-22 | The worker registers automatically everywhere except 127.0.0.1, localhost and [::1], where it needs ?sw=1 on the address. | While editing the app, an installed copy keeps serving old files until an update is accepted, which makes development confusing. What ships is what was tested: the same code path runs, only the trigger differs. |
| 2026-10-22 | The worker and the page treat the shared origin carefully: only caches named apogee-precache-<version> are ever deleted (on activate and on Reset offline copy), the page's registration is looked up by this app's own scope and a registration with any other scope is never touched, and only pages of this app (not test pages) may send the worker messages. | Every GitHub Pages site on the account shares one Cache Storage and one list of registrations (see the shared-origin entry above). A cleanup that deleted every cache or every registration would damage a neighbouring site. |
| 2026-10-22 | The browser test pages are never served from the offline copy: the worker identifies the requesting page by the clientId the browser puts on every request, including modules imported by other modules, and sends requests from pages under /tests/ to the network. Tests that exercise Reset offline copy use their own cache prefix and an address of their own, so running the test page never removes the installed app's offline copy. | Without this, the test page would run against the installed (possibly stale) code instead of the current files. A stale-cache experiment in headless Chrome showed the test page receiving the current file while the app received the cached one. Another experiment showed why the second rule is needed: an early version of the reset test removed the real worker and cache. |
| 2026-10-22 | tools/serve.js sends sw.js its own policy ("default-src 'none'; script-src 'self'; connect-src 'self'") because a worker obeys the policy sent with its own script, not the page's, and the page's policy has connect-src 'none'. On GitHub Pages no headers can be sent, so the worker there has no policy of its own; only the guard test and review limit what it can do. | Found while designing the worker: the page's policy would have stopped the worker from fetching its own app files on the local server. The meta tag (page policy) adds manifest-src and worker-src 'self'. |
| 2026-10-22 | An app added to an iPhone's Home Screen is expected to keep storage separate from Safari's tabs, so data has to move between them with Export and Import. Not verified on a device. | Reported behaviour of WebKit; the export and import screens are the supported way to move data, and the TODO lists the check. |
| 2026-10-23 | The dark theme's background is #000000 (was #131311), and its meta theme-color matches. | Owner's request for a black design. Only the dark theme changed; the light theme is unchanged. |
| 2026-10-23 | lastExportAt is written only when the user taps "I saved the file" after an export. Starting a download (or showing the export text) writes lastExportAttemptAt instead. Generating an export no longer writes lastExportAt. | The browser gives no event when a download finishes, and iOS can fail a download silently, so the app cannot know a file was saved. The user's own confirmation is the only signal that matches what the reminder claims. The attempt time is kept separately so the screen can say an export was started but not confirmed. |
| 2026-10-23 | The text copy path ("Show export as text") uses the same "I saved the file" confirmation as the download. Showing the text records an attempt only. | A copied text is a backup only if the user says they saved it, the same as a file. Using one confirmation keeps the two paths consistent. |
| 2026-10-23 | The backup reminder appears when the last confirmed export is more than 14 days old, or when there is no confirmed export and at least one workout is logged. Dismissing it hides it for 7 days (reminderDismissedUntil in meta). The rule is a pure function in src/domain/backup-reminder.js. | The owner asked for these thresholds. Keeping the rule pure makes it testable in Node. Meta is not exported, so the dismissal and the timestamps stay on this device and do not restore with a backup. |
| 2026-10-23 | persist() is called on every launch (feature-detected, never assumed), and the latest result and time are stored in meta as persistStatus. The launch call is not awaited, so the app opens without waiting for a browser permission prompt. The Backup tab shows "Storage protected" when persisted, and "Not guaranteed, back up regularly" otherwise. | The browser may change its answer between launches, so only the latest result is honest. A prompt that blocks startup would stop the app opening. |
| 2026-10-23 | Unverified and open: whether persist() is granted in Safari tabs and in iPhone Home Screen apps. The owner's earlier device test returned false on iPhone Safari and Firefox Focus. WebKit says Home Screen apps get heuristic treatment (not confirmed on a device). | Reported browser behaviour is not reliable enough to promise protection. The status line says "Not guaranteed" unless the browser agrees. |
| 2026-10-23 | lastExportAt values written by earlier builds (at generation) are not migrated. They are not confirmations, but the reminder still reads them. | Changing or deleting stored values on upgrade is a data migration; the owner has not decided it. Flagged for review. | 2026-10-23 | In the dark theme the accent (selected tabs, primary buttons, selected unit, update banner border) is white #ffffff, with black #000000 text on it. It was mint #78c7a8 with dark green text. | Owner's request to remove mint and green from the dark theme only. Black text on white keeps the contrast; the light theme keeps its green accent. |
| 2026-10-23 | One-time migration at launch: if meta has no exportConfirmationVersion, an existing lastExportAt (written by earlier builds when an export was generated) moves to lastExportAttemptAt, only if that is empty or older. lastExportAt is then deleted and exportConfirmationVersion = 1 is set, all in one transaction. When the version exists the migration does nothing, so a lastExportAt confirmed by the new flow is never touched. A failure leaves the old data as it was and the app opens anyway; it is retried next launch. | Earlier builds recorded the time an export was generated, which is not a confirmed backup, and the reminder would have trusted it: it could stay quiet after a download that was never saved. Moving it to the attempt keeps what happened visible ("started but not confirmed") without claiming a backup. The version flag makes it run once, and the single transaction means a crash cannot lose the old value. |

Log real workouts only in the Safari Home Screen app. The owner tested Firefox Focus's erase button, and it wiped the workouts logged in this app. The Safari Home Screen export and import round trip was tested on a real iPhone and matched (reported by the owner). | Focus is designed to clear site storage, and the app cannot prevent that, so its data there is not safe. | 2026-10-23 | Unchecked sets are planned rows kept in meta (key workoutPlan: { exercises, rows }), not sets with completedAt = null. Checking a row creates a real set with the same id; unchecking deletes that set and makes the row again. The sets store holds only logged sets. | completedAt is optional in the model and existing fixtures (and any future importer for apps that do not record a completion time) have logged sets with completedAt = null, so null cannot mean unchecked. With planned rows outside the sets store, history counts, the import preview, exports and the reminder cannot see unchecked sets, with no change to any of them and no schema change. Tests prove it. The cost: planned rows are not exported, so they are not in a backup and are lost if site data is cleared. |
| 2026-10-23 | A row can be checked only when reps is a whole number from 1 to 1000 and weight is a number from 0 up to 2500 kg, both typed (blank is refused, bodyweight is an explicit 0), in kg or lb. A refused check leaves the row unchecked and keeps what was typed. | The same strict rules as logging a set before (blank never becomes 0). The check goes through the same createWorkSet validation, so the limits cannot drift apart. |
| 2026-10-23 | The one running rest timer is stored in meta (key runningTimer: { setId, startedAt, endsAt }, absolute times in ms), so it is never exported. The remaining time is always endsAt minus the clock, on every tick (4 a second, only while a timer runs) and when the page becomes visible; it is clamped to between 0 and the full rest, so a clock jump forward ends the timer and a jump back never shows more than the full rest. A timer that ran out while the app was closed shows as done. A timer whose set no longer exists is never reported and is removed. | Counting down a stored number drifts and survives nothing; an absolute end does. A separate timer record (rather than deriving it from the latest checked set) is needed because a set that was put in done by a newer check must stay done even if the newer one is unchecked. |
| 2026-10-23 | Only one timer runs: checking a set replaces the timer, so the earlier set is done for good. Unchecking the set that owns the timer stops it and no other set takes over. Deleting that set, discarding or finishing the workout, or importing a backup also clears it. A warm-up set has no timer line and neither starts nor stops a timer. | This is the behaviour in the owner's sketch. Clearing happens in the same transaction as the change that causes it, so a crash cannot leave a timer for a set that is gone. There is no way to mark a set as warm-up in the screen yet; the rule applies to warm-up sets that already exist in stored data or imports. |
| 2026-10-23 | Rest values (Step A): every set rests 3:00 by default. A set's rest is edited by tapping its time (m:ss from 0:00 to 60:00; a bare number is refused because 90 could mean seconds or minutes). Checking writes the resolved rest into the set, so a done set keeps the rest it was logged with and cannot be edited by tapping its time (uncheck it first). Editing a resting set recomputes the end from the start time and ends the timer at once if the new rest is not longer than the elapsed time. | The stored restSeconds field already existed (null, unused), so there is no schema change. Confirming removes them and clears the timer in the same transaction as saving the end time. A workout with no checked set cannot be finished. The old Log set form is gone: the exercise picker adds an unchecked row, Add set adds another, and unchecking is the only way to change a logged set. logSet stays in the logger for tests and a later importer but the screen no longer uses it. | Unchecked sets are not part of the workout, and silently dropping them could lose a plan the user meant to do. | 2026-10-23 | Check (create the set, remove the planned row, start the timer) and uncheck (delete the set and its entry if empty, restore the row, clear the timer) are each ONE transaction, and a failure undoes all of it; both are tested by making the last write fail. Unchecking brings back the same reps, weight, unit and rest as numbers; the text is written in the plain form ("62,5" returns as 62.5, " 8 " as 8), and toggling any number of times never changes a value. | The owner asked for it to be confirmed. | 2026-10-23 | An untouched row made by Add set counts as typed: its reps and weight are filled in from the previous set (the last logged set or the last unchecked row of that exercise), and tapping the check logs them. Only a truly blank field is refused (the first row of an exercise with nothing to copy from). | 2026-10-23 | Importing a backup removes the planned sets and the running timer in the SAME transaction as the data it replaces, so a restore either replaces everything or nothing; a refused file leaves them alone. | 2026-10-23 | Two tabs: every session write (planned rows, checks, unchecks, deletes, finish, discard, rest changes, Update Rest Timers, and the tidy-ups on read) carries the plan's revision number and the store checks it INSIDE the write transaction (compare-and-set). A write made from a stale read is refused before anything changes; the operation reads again and redoes its work on the newer data (up to 5 times), so two tabs adding rows at once keep both rows, and a tab checking a row the other tab deleted gets "not planned" and logs nothing. Not covered: a tab does not redraw by itself when another tab changes the data (it shows the old state until its next action or tab change; every action reads fresh data first), and the History delete and the old logSet path do not use the revision. | A stale copy must never overwrite newer data. | 2026-10-23 | If site data is cleared (or the browser evicts the site), EVERYTHING in the browser goes: logged sets and workouts as well as planned rows and the timer, because they are all in the same IndexedDB. | 2026-10-23 | Schema version 2: an exercise has defaultRestSeconds (null = the app default 3:00, or a whole number of seconds from 0 to 3600). | 2026-10-23 | The upgrade from version 1 to 2 runs INSIDE the IndexedDB upgrade transaction (src/storage/migrations.js, called from the adapter): every exercise without the field gets defaultRestSeconds null, and the stored schemaVersion is set to 2, atomically with the version bump. If any step throws, the transaction is aborted: the database stays at version 1 with all its data and the open fails with a clear message. Export writes the code's SCHEMA_VERSION constant, never the stored value, and fills in a missing field, so a file is always complete. | One transaction means no half-upgraded state and no moment where a version 2 build runs on version 1 data. The steps are a list, so later versions chain. Tested with the steps on their own in Node, and on a real populated version 1 database in headless Chrome (the test page and the real app), including a forced failure that must roll back. |
